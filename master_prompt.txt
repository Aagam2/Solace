# Solace — Complete Development Prompt for Codex

I recommend building **Solace as a local-first desktop journaling application**, with an architecture that can eventually support AI-powered memory retrieval.

The idea is to build something more powerful than a traditional diary: a personal archive where you can record your experiences, attach photographs and videos, organize memories, and eventually ask questions about your past.

For example, you should eventually be able to ask:

- "What was I doing around November 15, 2026?"
- "When did I last meet Rahul?"
- "What books was I reading in August?"
- "Find the entry where I mentioned having an argument with someone."
- "Summarize everything interesting that happened in October."
- "What have I written about my career over the last six months?"

### Recommended technology stack

| Component | Technology |
|---|---|
| Desktop framework | Wails v3 |
| Backend | Go |
| Frontend | React + TypeScript |
| Styling | Tailwind CSS |
| UI components | shadcn/ui |
| Database | SQLite |
| Text editor | Tiptap |
| Full-text search | SQLite FTS5 |
| Images/videos | Local filesystem |
| State management | Zustand, where necessary |
| Data fetching | TanStack Query, if useful |
| Export | Markdown, HTML, JSON, ZIP |
| Future AI | Local or optional external LLM |
| Future semantic search | Embeddings and vector search |

**Why Wails v3?** Wails v3 was officially released on October 26, 2026, and is now the stable version recommended for new projects. It supports React, TypeScript, Go services, generated bindings, and native desktop functionality. [Wails](https://wails.io/blog/wails-v3-released/?utm_source=chatgpt.com)

SQLite's FTS5 extension is particularly useful because it provides indexed full-text search without requiring a separate search service. [SQLite](https://www.sqlite.org/fts5.html?utm_source=chatgpt.com)

### Development approach

I would divide the project into **nine parts**.

| Part | Focus | Outcome |
|---|---|---|
| 1 | Project setup and architecture | Working Wails application |
| 2 | Diary CRUD and date ranges | Create and manage entries |
| 3 | Rich-text editor and media | Images, videos, formatted text |
| 4 | Calendar, timeline, and navigation | Browse past entries |
| 5 | Search and organization | Find memories quickly |
| 6 | Export, import, and backup | Portable, recoverable data |
| 7 | Privacy and reliability | Safe long-term personal storage |
| 8 | Desktop polish and packaging | Usable standalone application |
| 9 | Future AI architecture | Foundation for querying your memories |

**Important:** Codex should complete one part at a time, run tests, and stop for your approval before starting the next part. That way, you can actually use the application throughout development rather than discovering problems after everything has been implemented.

## Master Codex Prompt

Copy the following into Codex.

# Project: Solace
## A Local-First Personal Diary and Memory Archive

You are a senior software engineer, desktop application architect, and UI/UX designer.

Your task is to design and implement a production-quality personal diary desktop application called **Solace**.

Solace is a private, offline-first personal journaling application that allows users to record daily experiences, memories, thoughts, photographs, videos, and other personal information.

The long-term vision is to transform Solace into a personal memory archive that can eventually be queried using an LLM.

For now, the application must work completely offline.

This is a real application intended for daily use over many years, not a prototype or demonstration.

Prioritize maintainability, performance, data integrity, reliability, and user experience.

# PART 2 — DIARY ENTRIES AND DATE RANGES

## Objective

Implement complete diary entry management.

This is the application's central feature.

## Entry Types

Support:

1. Single-day entries.
2. Multi-day entries.
3. Multiple entries on the same date.
4. Entries created retroactively.
5. Draft entries.
6. Entries without titles.

Do not enforce a one-entry-per-day restriction.

## Entry Data Model

Each entry should contain:

- Unique ID.
- Optional title.
- Rich-text content.
- Plain-text representation.
- Start date.
- End date.
- Created timestamp.
- Updated timestamp.
- Optional mood.
- Favorite status.
- Draft status.
- Optional location text.
- Tags.
- Attachments.
- Optional user-defined display order.

Use UUIDs or another stable ID strategy that will remain suitable for importing and exporting entries.

Store journal dates separately from creation timestamps.

Use unambiguous date representations.

Journal dates must not shift because of UTC conversion or daylight saving time.

## Date Range Semantics

A journal entry covers an inclusive date range:

[start_date, end_date]

Examples:

November 15 – November 16:

- Appears on November 15.
- Appears on November 16.
- Remains one underlying entry.

November 15 – November 20:

- Appears in calendar views for all six dates.
- Is not duplicated in the database.

Allow editing the start and end dates.

Validate:

start_date <= end_date

Allow multiple entries with overlapping ranges.

Do not automatically merge entries merely because their dates overlap.

## Core Operations

Implement:

- Create entry.
- Read entry.
- Update entry.
- Delete entry.
- List entries.
- Duplicate entry.
- Mark favorite.
- Remove favorite.
- Save as draft.
- Publish draft.
- Change dates.
- Edit title.
- Edit content.

Deletion should initially use a recoverable trash system.

Permanent deletion should require confirmation.

## Entry Editor

The entry creation workflow should be intuitive.

When creating an entry:

1. Default to today's date.
2. Allow changing the start date.
3. Allow specifying an optional end date.
4. Allow entering a title.
5. Allow writing content.
6. Allow saving.

Provide a clear date-range selector.

For example:

Date: November 15, 2026

Checkbox or toggle:
"Spans multiple days"

If enabled:

Start: November 15, 2026
End: November 16, 2026

The interface should display:

November 15–16, 2026

Handle ranges crossing months and years correctly.

## Autosave

Implement safe autosaving.

Requirements:

- Debounced saving.
- Visible save status.
- No unnecessary database writes.
- No loss of previously saved content.
- Save pending changes when navigating away.
- Handle write failures visibly.
- Prevent stale writes from overwriting newer content.

Consider preserving a recoverable local draft when a database write fails.

## Entry Listing

Display entries ordered by journal dates.

Provide:

- Newest first.
- Oldest first.
- Recently updated.
- Favorites first.

Show useful metadata:

- Title.
- Date or date range.
- Short content preview.
- Attachment count.
- Mood.
- Tags.

## Tests

Test:

1. Creating a single-day entry.
2. Creating a multi-day entry.
3. Creating multiple entries on the same date.
4. Editing an entry.
5. Deleting and restoring an entry.
6. Saving a draft.
7. Editing dates.
8. Entries spanning month boundaries.
9. Entries spanning year boundaries.
10. Invalid date ranges.
11. Retroactive entries.
12. Restarting the application after saving.
13. Autosave under rapid editing.
14. Date ranges overlapping each other.

## Manual Acceptance Test

# PART 7 — PRIVACY, RELIABILITY, AND DATA SAFETY

## Objective

Make Solace suitable for long-term private use.

## Privacy

The application must not:

- Upload diary entries.
- Contact analytics servers.
- Collect telemetry.
- Require accounts.
- Send crash reports automatically.
- Read unrelated user files without authorization.

Network access must not be required for normal operation.

If future functionality requires network access, it must be explicitly opt-in.

## Data Safety

Implement:

- SQLite foreign keys.
- Database integrity checks.
- Migration versioning.
- Safe migration failures.
- Backup before potentially destructive migrations.
- Appropriate filesystem permissions.
- Graceful disk-full handling.
- Graceful handling of unreadable or missing files.

Do not silently delete damaged data.

## Entry Recovery

Implement a trash system.

## Additional recommendations

There are a few decisions I'd make now rather than leave until much later.

### 1. Treat export and backup as different features

This distinction matters a lot.

**Export** produces something you can read independently of Solace. For example, a folder containing Markdown entries and their photographs.

**Backup** produces something Solace can restore without losing metadata, formatting, relationships, or files.

I recommend implementing both. SQLite provides supported mechanisms for creating consistent database snapshots, which should be used for backups rather than directly copying a database while it is being written to. [SQLite](https://www.sqlite.org/backup.html?utm_source=chatgpt.com)

### 2. Keep dates separate from timestamps

For your November 15–16 example, I would store:

| Field | Value |
|---|---|
| Entry ID | `abc-123` |
| Start date | 2026-11-15 |
| End date | 2026-11-16 |
| Created at | 2026-11-20 21:30 |
| Updated at | 2026-11-21 10:15 |

This makes querying historical events, calendar rendering, and future LLM retrieval much more reliable.

### 3. Don't implement the LLM immediately

Build the foundation first:

**Phase A — Keyword search:** Find entries containing specific words using SQLite FTS5.

**Phase B — Semantic search:** Find related content even when the exact words differ.

**Phase C — AI memory retrieval:** Ask questions and get answers grounded in relevant entries.

**Phase D — Memory analysis:** Summarize periods, identify recurring themes, and connect related experiences.

I'd also keep the original diary entries immutable from the AI's perspective: AI should never silently rewrite what you recorded.

### 4. Make the media library portable

For photographs and videos, keep files on disk rather than directly in SQLite.

For example:

```text
solace/
├── solace.db
├── media/
│   ├── images/
│   │   ├── 019a....jpg
│   │   └── 019b....png
│   ├── videos/
│   │   └── 019c....mp4
│   └── documents/
├── thumbnails/
└── backups/
```

This will make backups, exports, and migration to another computer much easier.
